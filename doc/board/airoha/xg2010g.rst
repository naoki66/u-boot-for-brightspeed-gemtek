XG2010G U-Boot
==============

本文档记录 XG2010G 的 U-Boot 板级配置、启动链和 NAND 布局。
XG2010G 使用 Airoha AN7581 类 SoC。当前配置基于上游 U-Boot 已有的
AN7581 支持，并在本项目中加入 XG2010G 的板级设备树。

安全提醒
--------

刷写 bootloader 或 NAND 前必须准备完整的原厂备份，并确认 NAND 型号、
容量、页大小、擦除块大小、ECC/OOB 方式和 BootROM 的镜像格式完全匹配。
错误的 mtd0 镜像可能导致设备无法从 NAND 启动；本项目不提供盲刷命令。

除 ``board/airoha/xg2010g/firmware`` 下明确记录 SHA256 的最小启动输入外，
本仓库不得提交以下内容：

* 完整原厂 mtd0、完整固件备份或未筛选的原厂二进制；
* 签名私钥、密钥目录、签名配置和未公开的证书材料；
* 仅适用于单台设备的序列号、MAC 地址或工厂校准数据；
* 构建目录和未经验证的最终刷写镜像。

启动链
------

AN7581 类平台的典型启动顺序如下：

1. 片内 BootROM 从 NAND 的启动位置读取启动镜像。
2. BootROM 启动 BL2。BL2 负责早期硬件初始化，尤其是 DDR 初始化，
   并根据平台策略验证和装载后续组件。
3. BL2 装载 BL31。BL31 是 ARM Trusted Firmware 的 EL3 运行时固件，
   负责安全监控器和安全世界/普通世界切换。
4. BL31 将控制权交给 BL33。这里的 BL33 通常就是 U-Boot。
5. U-Boot 访问 NAND 上的 UBI/UBIFS 或 FIT 镜像，最后启动 Linux。

因此，单独编译出来的 ``u-boot.bin`` 通常不能直接替代完整的 mtd0。
在使用 FIP 启动的设备上，mtd0 中应是与该平台 BootROM/BL2 约定的完整
FIP，而不是只有 BL33 的裸 U-Boot。

BL2、BL31 和签名材料
--------------------

BL2 负责早期硬件与 DDR 初始化，BL31 提供 EL3 运行时环境。本项目使用固定版本的
Airoha TF-A 树（``Yuzhii0718/atf-airoha``，v2.15.0 基线）、Mbed TLS 和
Arm GNU Toolchain 从源码构建这两个阶段：

* BL21、BL22、BL23 分三次编译，再与 NAND flash table 组装为 BL2；
* BL31 编译后使用 Airoha 兼容的 LZMA 4.65 格式压缩；
* 本项目 U-Boot 经 LZMA 压缩后作为 BL33 载荷；
* ``cert_create`` 和 ``fiptool`` 生成证书链与完整 FIP。

原厂 FIP 的证书链不能因为只替换了 BL33 就默认继续有效。若证书中包含
BL33 的摘要，替换 BL33 后必须重新生成对应的内容证书和签名；若设备要求
固定签名根，还必须使用设备认可的签名根。没有正确的签名密钥
或密钥授权时，新 FIP 可能在 BootROM 或 BL2 阶段被拒绝。

已从原厂 mtd0 备份确认其包含 FIP 头 ``0xaa640001``，且 FIP 位于 mtd0
偏移 ``0x800``。备份中可见 BL2、BL31、BL33/U-Boot 和签名证书。
下面这些偏移仅用于分析原厂文件，不能当作所有 XG2010G 设备的
通用格式：

* BL2：FIP 相对偏移约 ``0x400``；
* BL31：FIP 相对偏移约 ``0x1f800``；
* BL33：FIP 相对偏移约 ``0x29c00``。

重新组装 FIP 时应以目标平台提供的 ``fiptool``、FIP UUID 定义、载入地址、
对齐要求和签名配置为准。不要把本仓库的 U-Boot 配置误认为已经完成了
Airoha 私有 FIP 签名流程。

当前仓库只保留从 ``original-device-backup-20260816/mtd0-bootloader-stock.bin``
提取的 mtd0 前导区：

   * - 文件
     - 说明
     - SHA256
   * - ``board/airoha/xg2010g/firmware/mtd0-prefix.bin``

NAND 分区
---------

按当前目标设备的 512 MiB NAND 规划，分区如下。地址和大小均为字节：

.. list-table::
   :header-rows: 1
   :widths: 25 20 20 35

   * - 分区
     - 起始
     - 结束（不含）
     - 用途
   * - ``bootloader``
     - ``0x00000000``
     - ``0x00200000``
     - 2 MiB，完整启动镜像/FIP，只读保护
   * - ``uenv``
     - ``0x00200000``
     - ``0x00400000``
     - 2 MiB，U-Boot 环境所在区域
   * - ``dsd``
     - ``0x00400000``
     - ``0x00600000``
     - 2 MiB，保留原有数据
   * - ``ubi``
     - ``0x00600000``
     - ``0x1be00000``
     - 440 MiB，项目唯一系统 UBI，必须包含 ``fit`` 卷
   * - ``reserved_bmt``
     - ``0x1be00000``
     - ``0x20000000``
     - 66 MiB，坏块替代和 BMT 预留，只读保护

这里的 ``ubi`` 是给 UBI 使用的 MTD 分区；“UBI 2.0”表示目标系统的
UBI 分区/布局约定，不是 U-Boot 中需要选择的另一个 UBI 工具版本。
UBI 会根据 NAND 的实际擦除块和坏块情况管理可用 PEB。尾部预留区不能
被系统镜像、UBI 镜像或升级脚本覆盖。原厂 TTL 中的 ``tclinux``、
``tclinux_slave``、``system`` 仅用于校核，不属于本项目兼容布局。TTL
确认本板使用 512 MiB W25N04K，擦除块 128 KiB、页 2 KiB、OOB 128 字节；
项目 U-Boot/Recovery 会拒绝不符合该几何和 440 MiB 分区大小的 ``ubi``。
板级初始化会自动清理原厂 ``ubi.mtd=system/tclinux*`` 和
``root=/dev/mtdblock*`` 参数，避免 Linux 误挂载原厂分区。

bootargs 参数说明
------------------

本节根据 XG2010G 原厂 TTL、Airoha/ECONET SDK 启动参数解析代码和实机 PHY
初始化日志校核。文档或聊天中出现的 ``\_`` 只是 Markdown 转义，实际参数名中
只有普通下划线，不能把反斜杠传给内核。

``onu_type``、``qdma_init``、``bootflag`` 和 ``serdes_*`` 由 SDK 使用
``%x``、``%hx`` 或 ``%hhx`` 解析，因此没有 ``0x`` 前缀时仍按十六进制解释。
例如 ``onu_type=71`` 实际是 ``0x71``，``qdma_init=69bb`` 实际是
``0x69bb``。

GPIO/LED 兼容字段
~~~~~~~~~~~~~~~~~

``ether_gpio=0c``、``dsl_gpio=0b`` 和 ``internet_gpio=02`` 是原厂平台的
单字节指示字段；``power_gpio=1515`` 是厂商打包字段，不能按十进制 GPIO 1515
理解。``multi_upgrade_gpio=0b020400000000000000000000000000`` 是 16 字节升级
状态 GPIO/LED 配置表，不是单一 GPIO 编号。当前公开 SDK 只列出这些环境变量名，
没有给出 ``power_gpio`` 和 ``multi_upgrade_gpio`` 的完整打包格式，未取得厂商
解码实现前不应自行改写。

非 BBF.247**。这与原厂 TTL 中的 ``PON MAC GET ONU_TYPE = SFU`` 和
``PON MAC GET ONU_MODE = XGSPON`` 完全一致。

QDMA：``qdma_init=69bb``
~~~~~~~~~~~~~~~~~~~~~~~~

``0x69bb`` 的有效配置为：LAN/WAN payload selector 均为 ``3``（256 字节档），
LAN/WAN DSCP/描述符均走 SRAM，并开启 ``FAST_WAN``、``FAST_XSI_PCIE1``、
``FAST_XSI_ETHER``、``FAST_XSI_PON``。EN7581 SDK 因此预留 LAN 4 MiB、WAN 5 MiB，
合计 9 MiB；原厂 TTL 的 ``0x400000``/``0x500000`` 输出与此一致。

SerDes 参数
~~~~~~~~~~~

EN7581 使用六个独立的 ``serdes_*`` 参数。每个值是 12 位十六进制配置字：

.. code-block:: text

   [11:8] PHY 类型
    [7:4] Ethernet 类型：0=无，1=LAN，2=WAN
    [3:0] 当前 SerDes 通道的接口选择

.. list-table::
   :header-rows: 1
   :widths: 28 38 34

   * - 参数
     - 解码
     - 实机对应
   * - ``serdes_pon=000``
     - 原生 PON 接口，Ethernet/PHY 字段为零
     - XGS-PON
   * - ``serdes_ethernet=411``
     - PHY profile C + LAN + USXGMII
     - RTL8261N，MDIO 地址 5
   * - ``serdes_wifi1=005``
     - WiFi1/PCIe0 选择 ``NONE``
     - 通道关闭
   * - ``serdes_wifi2=413``
     - PHY profile C + LAN + USXGMII
     - PCIe1 通道改作 RTL8261N Ethernet，MDIO 地址 8
   * - ``serdes_usb1=111``
     - AN8811 profile + LAN + HSGMII
     - USB1 通道改作 EN8811H 2.5G，MDIO 地址 ``0xf``
   * - ``serdes_usb2=000``
     - USB3 接口，Ethernet/PHY 字段为零
     - 未改作 Ethernet

``WiFi2``、``USB1`` 是 SoC SerDes 复用通道名称，不表示设备实际装有 Wi-Fi
或使用 USB 功能。``serdes_sel=0`` 在 EN7581 分支主要是兼容残留，不会覆盖六路
独立配置。原厂 ``serdes_ethernet=411`` 不应改成 ``421``，后者会把 Ethernet
SerDes 的角色从 LAN 改成 WAN，和原厂 TTL 及端口映射不符。

对应到完整硬件映射：``gdm4`` + FE MDIO ``phy5`` 是 LAN1/WAN 10G
RTL8261N 口，``gdm3`` + FE MDIO ``phy8`` 是 LAN2 10G RTL8261N 口。
LAN3 是原厂 ``eth0.5`` 的 USB1 XSI/HSGMII 通道，复用 ``gdm4`` 但使用
独立的 QDMA/XSI 子通道，外接 MDIO ``0x0f`` 的 EN8811H 2.5G PHY。当前
U-Boot recovery DTS 不启用这些外部 XSI 口，仅启用 ``gdm1``。

刷写边界
--------

升级系统时只允许操作 ``ubi`` 分区，即 NAND 偏移
``0x00600000`` 起、长度 ``0x1b800000`` 的范围。升级流程应使用 MTD
分区名 ``ubi``，让 MTD/UBI 处理坏块，不应把整个 NAND 或 ``mtd0`` 当作
系统镜像目标。

bootloader 只允许在明确验证 FIP、签名、BL2/BL31 兼容性后替换
``0x00000000-0x00200000``。任何 bootloader 升级操作都必须保持
工厂校准分区 ``uenv`` 的 ``0x00200000-0x00400000`` 和 ``dsd`` 的
``0x00400000-0x00600000`` 原样不变。``reserved_bmt`` 也不得写入。

U-Boot 配置
-----------

构建配置为 ``configs/xg2010g_defconfig``。它启用：

* AN7581 CPU、DDR、UART 和 SPI-NAND/SNFI；
* MTD、固定分区、UBI 和 UBIFS 命令；
* 将环境放在 ``spi-nand0`` 的绝对偏移 ``0x00200000``；
* 以 ``xg2010g`` 作为默认设备树。

由于 XG2010G 的板级 DTS 尚未进入 Linux 的 dts/upstream，本项目有意关闭
``CONFIG_OF_UPSTREAM``，而在 ``arch/arm/dts`` 维护很小的板级文件。
SoC 级 DTS 仍然引用 U-Boot 已同步的 Airoha ``en7581.dtsi``。

GitHub Actions 签名构建
-----------------------

仓库的 ``.github/workflows/build-mtd0.yml`` 用于在 GitHub Actions 上强制
构建 signed ``mtd0``；不再提供 ``skip``/未签名选项，也不会上传未签名
artifact：

* 编译 ``xg2010g_defconfig``，将 ``u-boot.bin`` 压缩为 BL33 载荷；
* 构建 TF-A 的 ``fiptool`` 和 ``cert_create``；
* 从固定的 Airoha TF-A 源码构建 BL2 和 BL31；
* 使用仓库内置的 mtd0 前导区，也可用 Secret 或私有 URL 覆盖；
* 使用 ``cert_create`` 为 ``--tb-fw`` BL2、``--soc-fw`` BL31 和
  ``--nt-fw`` BL33 压缩载荷生成证书链；
* 使用 ``fiptool create`` 生成 signed FIP；
* 将 FIP 写入 2 MiB mtd0 镜像中的 ``0x800`` 偏移，前导区保持原厂内容，
  其余尾部填充 ``0xff``。

默认仓库变量（每板各自一份，以 ``${BOARD_UPPER}_*`` 命名；XG2010G 见
下表，XR1710G 见 :doc:`xr1710g`）如下：

.. list-table::
   :header-rows: 1
   :widths: 30 20 50

   * - 变量

mtd0 前导区：原厂前缀或已擦除（0xFF），不能用零填充
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``mtd0`` 的 ``0x0000..0x07ff`` 不是留白，但也不需要专门写什么"引导代码"。原厂
U-Boot 自带的 TFTP 刷写助手说明了它到底是什么：

.. code-block:: text

   boot_tftp_write_bl2=mw.b $loadaddr 0xff 0x20000
                       setexpr loadaddr_bl2 $loadaddr + 0x800
                       tftpboot $loadaddr_bl2 $bootfile_bl2 && run mtd_write_bl2
   mtd_write_bl2=itest.l $filesize -le 0x1f800 && mtd erase bl2 && \
                 mtd write bl2 $loadaddr 0 0x20000

即原厂把一个正好 2 MiB 的缓冲区**整块填 0xFF**，FIP 放在 ``+0x800``，然后整
2 MiB 写进分区。所以前导区的合法取值是：

* **已擦除**（全 ``0xFF``）—— 原厂做法；
* **原厂前导区**（``mtd0+0`` 是 ARM NOP 滑板 ``0xe320f000``）—— 仓库的
  ``MTD0_PREFIX_MODE=stock``，最保守，原样保留本机原厂数据。

**零填充（全 ``0x00``）不是合法取值**：它既不是原厂前缀、也不是已擦除的 flash，
用这种镜像刷机后设备不从 NAND 启动。CI 因此把 ``MTD0_PREFIX_MODE`` 固定为
``stock``，并彻底移除了旧的 ``zero`` 模式；U-Boot 恢复服务也同时拒绝全零前导区
（只接受 NOP 滑板或全 ``0xFF``）。

实测确认的 mtd0 字节布局（XG2010G）：

.. list-table::
   :header-rows: 1
   :widths: 22 20 58

   * - mtd0 偏移
     - 长度
     - 内容
   * - ``0x000000``
     - ``0x800``
     - 原厂前导区（首字 ``e320f000``）或全 ``0xFF``；**不能是 0x00**
   * - ``0x000800``
     - ``0x10``
     - FIP 头：magic ``0xaa640001``、serial ``0x12345678``、platform ToC flags
   * - ``0x000810``
     - ``40 × N``
     - FIP ToC 条目：UUID(16) + 偏移(8) + 长度(8) + flags(8)
   * - ``0x000C00``
     - ``0x1a394``
     - BL2 载荷（FIP 相对 ``0x400``）
   * - ``0x001B000``
     - ``0xad64``
     - BL31
   * - ``0x0026000``
     - ``0x49c97``
     - BL33 / U-Boot
   * - ``0x0070000``
     - ...
     - 证书链（到 ``0x73248`` 结束）
   * - ``0x073248``
     - ``0x18cdb8``
     - ``0xFF`` 填充到 2 MiB

串口 TFTP 救砖与启动菜单
------------------------

X 模式依赖 BootROM 和串口，Web Recovery 依赖 U-Boot 的 lwIP 网络栈。两者都可能
不可用（网口没起来、镜像已经不能启动、恢复页挂了）。因此在 U-Boot 里再提供一条
**纯串口 + TFTP** 的写入通道，设计抄自原厂 U-Boot 的
``boot_tftp_write_bl2`` / ``mtd_write_bl2`` 助手和它的启动菜单。

默认环境变量（``board/airoha/an7581/xg2010g.env`` 与共用的
``xg2010g-tftp.env``）：:

    ipaddr=192.168.0.1      netmask=255.255.255.0      serverip=192.168.0.254
    tftpboot_addr=0x90000000        # 暂存区，刻意不用 $loadaddr
    tftpverify_addr=0x94000000      # 读回比对区
    tftpboot_size=0x200000          # 完整 mtd0 镜像长度
    tftpboot_bl2_size=0x20000       # preloader 写入的擦除区长度

``tftpboot_addr`` 与 ``$loadaddr`` 分开是有意为之：Web Recovery 的上传缓冲在
``recovery_addr``（``0x81800000``），分开可以避免 TFTP 传输和正在进行的 HTTP
上传互相踩内存。

用法（所有助手都不会自动执行，只在手动或菜单里触发）：:

    setenv serverip 192.168.0.254
    setenv tftpboot_file xg2010g-2026-9-16-xxxxxxxxxxxx-mtd0-signed.bin
    run net_init
    run tftp_flash                 # 完整 mtd0 镜像 -> bootloader 分区

其余助手：

.. list-table::
   :header-rows: 1
   :widths: 26 74

   * - 变量
     - 作用
   * - ``run tftp_flash``
     - 写完整 2 MiB ``mtd0`` 到 ``bootloader`` 分区（自带 0x800 前导区）
   * - ``run tftp_flash_bl2``
     - 写 ``preloader.bin`` 这类自带 0x800 前导区的镜像。先用 ``iret`` 把
       ``0x20000`` 暂存区填 ``0xFF``，把文件放到 ``+0x800``，再整块写入
       —— 与原厂 ``mw.b $loadaddr 0xff 0x20000`` 完全一致
   * - ``run tftp_flash_fit``
     - 把系统固件写进 UBI 的 ``fit`` 卷
   * - ``run tftp_flash_uenv`` / ``run tftp_flash_dsd``
     - 恢复 2 MiB 的 ``uenv`` / ``dsd`` 出厂校准分区
   * - ``run tftp_flash_manual``
     - **手动指定写入地址**：写 ``${tftpboot_file}`` 到 ``${tftpboot_part}`` 的
       偏移 ``${tftpboot_ofs}``，长度 ``${tftpboot_len}``

手动指定地址写入（``tftp_flash_manual``）
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

固定助手只覆盖已知的几种布局；``tftp_flash_manual`` 是给"固定助手都不匹配"的
情况用的逃生口。它由三个变量决定写到哪：

.. list-table::
   :header-rows: 1
   :widths: 24 18 58

   * - 变量
     - 示例
     - 含义
   * - ``tftpboot_file``
     - ``my-image.bin``
     - TFTP 服务器上的文件名（相对于 TFTP 根目录）
   * - ``tftpboot_part``
     - ``bootloader``
     - MTD **分区标签**，必须与 ``mtd list`` 打印的 ``"..."`` 完全一致
   * - ``tftpboot_ofs``
     - ``0x800``
     - **相对该分区起始**的偏移（不是全片绝对地址）
   * - ``tftpboot_len``
     - ``0x200000``
     - 要擦除并写入的长度（字节）

它展开成这一串：

.. code-block:: text

   tftpboot ${tftpboot_addr} ${tftpboot_file}
   itest.l ${filesize} -le ${tftpboot_len}
   mtd erase ${tftpboot_part} ${tftpboot_ofs} ${tftpboot_len}
   mtd write ${tftpboot_part} ${tftpboot_addr} ${tftpboot_ofs} ${tftpboot_len}
   mtd read  ${tftpboot_part} ${tftpverify_addr} ${tftpboot_ofs} ${tftpboot_len}
   cmp.b ${tftpboot_addr} ${tftpverify_addr} ${tftpboot_len}

**偏移基准容易搞错：``tftpboot_ofs`` 是分区相对偏移，不是芯片绝对地址。**
``mtd read/write`` 内部用 ``get_mtd_device_nm("<part>")`` 取到的是**分区**的
``mtd_info``，命令里的 offset 从该分区开头算起。而 ``mtd list`` 打印的是**绝对**
地址，两者差一个分区起始地址。XG2010G 的对照：

.. list-table::
   :header-rows: 1
   :widths: 22 22 34 22

   * - 分区标签
     - 绝对起始
     - 大小
     - 写到分区开头时 ``tftpboot_ofs``
   * - ``bootloader``
     - ``0x00000000``
     - ``0x200000`` (2 MiB)
     - ``0``
   * - ``uenv``
     - ``0x00200000``
     - ``0x200000`` (2 MiB)
     - ``0``
   * - ``dsd``
     - ``0x00400000``
     - ``0x200000`` (2 MiB)
     - ``0``
   * - ``ubi``
     - ``0x00600000``
     - ``0x1b800000``
     - 用 UBI 卷接口，不要直接写

也就是说，要写 ``0x00200000`` 处的 uenv，正确写法是
``tftpboot_part=uenv`` + ``tftpboot_ofs=0``，**不是**
``tftpboot_part=bootloader`` + ``tftpboot_ofs=0x200000``——后者会写到
bootloader 分区越界处并被拒绝（``mtd read`` 会先报
``Offset not aligned`` 或超出分区）。

对齐与长度约束（来自 ``cmd/mtd.c`` 的实际检查）：

* ``mtd erase`` 的 offset 和 len 都必须**擦除块对齐**（本板 ``0x20000``）。不满足
  直接报错不执行。
* ``mtd read/write`` 的 offset 必须**页对齐**（本板 ``0x800``）；len 不对齐会被
  自动向上取整到页边界并打印提示。
* ``mtd write`` 在 NAND 上**默认跳过全 0xFF 的页**（"不写空页"）。这正好符合需求：
  已擦除区域本来就读作 0xFF，跳过可以避免无谓地覆盖擦除块、也避免误碰坏块标记。
  真需要强制写空页时用 ``mtd write.dontskipff``，但**一般不要用**
  （命令帮助里原话是 "don't use it if unsure"）。

完整示例——把一份自带 0x800 前导区的镜像写到 bootloader 分区开头：

.. code-block:: console

   setenv serverip 192.168.0.254
   setenv tftpboot_file xg2010g-preloader.bin
   setenv tftpboot_part bootloader
   setenv tftpboot_ofs  0
   setenv tftpboot_len  0x20000
   run net_init
   run tftp_flash_manual

写入前先确认目标，再备份：

.. code-block:: console

   mtd list                                  /* 看 "..." 里的分区标签与绝对地址 */
   ubi part ubi ; ubi info l                 /* 看 ubi 里的卷 */
   mtd read bootloader ${tftpverify_addr} 0 0x100
   md.b ${tftpverify_addr} 0x100             /* 看一眼现在的开头是什么 */

.. warning::

   手动模式**不做任何目标合法性检查**，既不校验文件类型、也不校验 offset 是否
   落在一个"应该写"的区域。这是它的用途，也是它的风险：

   * 写错 ``tftpboot_part`` 或 ``tftpboot_ofs`` 可能覆盖出厂校准数据
     （``factory`` / ``dsd`` / ``PON`` / ``BOSA``），且**不可恢复**；
   * 写坏 ``bootloader`` 会让设备只能走 X 模式或 NAND 编程器。

   所以：**写入前先用 Web Recovery 备份页把 ``bootloader``（mtd0）、
   ``uenv`` 和 ``dsd`` 下载到电脑**，并记录 ``mtd list`` 输出。网页只提供这
   三个 2 MiB 分区。``bootloader`` 里是完整启动链（BL2、BL31、本仓库
   U-Boot 及证书，位于原厂前导区之后），**无法由 ``uenv`` / ``dsd`` / UBI
   备份重建**，因此它是回原厂时必须先留下的那一个。``ubi`` 分区（440 MiB）
   网页不提供下载，需要时用串口 ``mtd read`` 分段读出。

每个助手在**写完都会读回比对**：``mtd read``（或 ``ubi read``）到
``${tftpverify_addr}`` 后 ``cmp.b`` 源缓冲，一致才打印
``... written and read-back verified.``，否则打印 ``FAILED`` 并保留已写内容不做
其它动作。这一步不能省：NAND 写入失败或碰到坏块时，不读回就"看起来成功"，而
镜像其实不能启动。

启动菜单（``run boot_menu``，或直接在 U-Boot 提示符敲 ``bootmenu``）：

.. code-block:: text

   0  Boot system                     run boot_ubi
   1  Web recovery                    run http_recovery
   2  Flash mtd0 image via TFTP
   3  Flash BL2/preloader via TFTP
   4  Flash system firmware via TFTP
   5  Manual NAND write via TFTP
   6  Show storage information        mtd list / ubi info l
   7  Show flash environment          printenv 相关变量
   8  Reboot                           reset

菜单是**可选**的：默认 ``bootcmd`` 仍是 ``run boot_ubi || http_recovery``，
所以无人值守开机时系统照常启动、启动失败照常落到 Web Recovery。菜单只是让这些
助手在没有网页面时也能用上。

X 模式救砖
----------

如果 mtd0 写坏导致 NAND 不能正常启动，Airoha BootROM 通常仍可进入串口
X 模式加载临时引导。该流程需要 TTL 串口和支持 XMODEM 的终端工具。

救砖链不需要 ``bootext.ram``：X 模式下直接发送 ``ubi-preloader.bin`` 即可
（见下文正式刷机步骤）。仅当设备无法直接接收 ``ubi-preloader.bin`` 时，才先
加载一次 ``bootext.ram`` 作为应急垫片：

1. 断电。
2. 按住 ``RESET`` 键，同时通电启动。
3. 终端显示 ``CCCC`` 时表示设备已进入 X 模式。
4. 在终端菜单中选择“文件 -> 传输 -> XMODEM -> 发送”。
5. 选择 ``bootext.ram``，等待传输完成后，再按下方正式刷机步骤继续。

正式刷机步骤如下：

1. TTL 进入救砖模式：断电后按住 ``RESET`` 键，同时通电启动；按 ``X``/``x``，
   终端显示 ``CCCC`` 后进入 XMODEM 接收。
2. 传输 BL2/preloader：选择“文件 -> 传输 -> XMODEM -> 发送”，发送
   Actions 产物中的 ``...-ubi-preloader.bin`` 或 ``ubi-preloader.bin``。
   传输完成后设备会自动重启。
3. 再次进入 X 模式：重新断电，按住 ``RESET`` 后通电；提示
   ``Press x to load BL31 + U-Boot FIP`` 时输入 ``x``。
4. 传输 BL31 + U-Boot FIP：再次选择“文件 -> 传输 -> XMODEM -> 发送”，
   发送 ``...-ubi-bl31-uboot.fip`` 或 ``ubi-bl31-uboot.fip``。
5. 关键时序：第二段 XMODEM 进度到 100% 前提前按住 ``RESET``，等待设备灯
   完成闪烁并进入流水式闪烁后再松开。
6. 浏览器使用无痕模式访问 ``http://192.168.0.1/``。必须用无痕（隐私）窗口：
   设备此前运行 OpenWrt 时，同一地址曾由 LuCI 提供 301 跳转到登录页
   ``http://192.168.0.1/cgi-bin/luci/``，普通窗口可能命中浏览器缓存的跳转记录，
   打开的是 OpenWrt 登录页而非 Recovery 页；若仍出现 LuCI 页面，按 ``Ctrl+F5``
   强制刷新。

   .. note::

      ``192.168.0.1`` 是 U-Boot 内置的默认恢复地址，与原厂 Web Recovery
      一致。若设备的 ``uenv`` 分区里已经保存了 ``ipaddr``，U-Boot 会沿用该
      地址而不是默认值；此时请以串口打印的
      ``recovery network: eth0/gdm1 1G switch port only, http://<addr>/``
      为准，或先执行 ``setenv ipaddr 192.168.0.1`` 再重试。
7. 选择 ``ubi-squashfs-sysupgrade.itb``；``BL2`` 选择
   ``...-ubi-preloader.bin``，``U-Boot`` 选择 ``...-ubi-bl31-uboot.fip``。
8. 系统固件上传会自动擦除并重建完整 UBI，等待数分钟完成刷写。
9. 刷写完成后务必断电重启设备。

若第二段出现 ``ERROR:   LZMA: res 2 state 0`` / ``Failed to decompress image``，
表示 BL23 已经进入第二阶段，但收到的 BL31 + U-Boot FIP 中的压缩镜像无效。先确认
第二次 XMODEM 发送的是同板型 ``...-ubi-bl31-uboot.fip``，而不是
``...-mtd0-signed.bin``、``...-fip-signed.bin`` 或 ``...-ubi-preloader.bin``；
再用 artifact 里的 ``sha256sums.txt`` 核对文件后重发。若校验正确仍失败，
继续确认 ``...-ubi-bl31-uboot.fip`` 是否超过 ``0x60000``；超过时 BL23
第二段 XMODEM 可能截断 FIP，表现为同样的 LZMA ``res 2``。

U-Boot 启动后会对 RESET GPIO 做确认：默认需要持续按住 3 秒才进入 Web
Recovery，并在串口打印倒计时。中途松开会取消恢复并继续正常启动。可通过环境变量
调整等待时间：

.. code-block:: console

   setenv recovery_button_timeout 5
   saveenv

设置为 ``0`` 可恢复为检测到按键后立即进入恢复。

``bootext.ram`` 属于平台救援链文件，不由本仓库的 U-Boot 编译生成；需要
保留已验证可用的原厂/平台版本。CI 产物附带自编译的
``<board>-...-bootext-bl2.bin``（BootROM 加载头 + 本仓库编译的 BL2）作应急
备份，但未经过真机验证，优先使用已验证的原厂版本。

建议的验证顺序
--------------

在 Linux/WSL 环境中，先执行：

.. code-block:: console

   make CROSS_COMPILE=aarch64-linux-gnu- xg2010g_defconfig
   make CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)

若在 Windows 的 ``/mnt/d`` 这类 drvfs 挂载上构建，必须确认 Git 符号链接
和脚本可执行位被正确保留。更稳妥的做法是在 WSL 的 Linux 文件系统中构建，
或使用 ``git archive`` 导出一份临时构建副本后再编译。

构建得到的 ``u-boot.bin`` 是 BL33 候选文件。它还需要按照目标平台的
FIP 流程封装，不能直接当作完整 mtd0 写入。

使用平台提供的 ``fiptool`` 时，概念上的流程是：

.. code-block:: console

   fiptool info original.fip
   fiptool create --tb-fw bl2.bin --soc-fw bl31.bin --nt-fw u-boot.bin new.fip

上面的命令只表示 FIP 中 BL2、BL31、BL33 的关系。真实设备通常还需要
平台专用的证书、密钥、UUID、载入地址、签名参数和可能的额外固件项；
不能直接照抄此示例生成可启动镜像。

将 FIP 放入 mtd0 时，还要确认原厂镜像的前导数据、FIP 在 mtd0 中的偏移、
NAND 坏块处理和 BootROM 的复制规则。建议先通过串口验证 U-Boot 能识别
NAND 和分区，再在 Linux 中确认 ``cat /proc/mtd`` 的边界与本 DTS 一致。

分区布局虽然只在设备树里描述一次，但却被四处独立引用：设备树的
``fixed-partitions``、板级 ``XG2010G_UBI_*`` 几何常量、TFTP 救援环境里的
尺寸断言、以及 CI 的 mtd0 镜像几何。另外 pinned TF-A 里的
``PLAT_ECNT_FIP_OFFSET`` / ``PLAT_ECNT_FIP_MAX_SIZE`` 决定了 BL23 会从 mtd0
的哪个偏移读多长的 FIP，因此 ``bootloader`` 分区必须能装下这个窗口。
``scripts/ci/check-partition-layout.py`` 把这些来源放在一起对拍：

.. code-block:: console

   python3 scripts/ci/check-partition-layout.py --board xg2010g
   python3 scripts/ci/check-partition-layout.py --board xg2010g \
       --atf-dir <tf-a 源码树> --require-atf

第二条命令需要 Airoha TF-A 源码树（CI 中是 ``trusted-firmware-a``），会额外
校验 FIP 窗口、偏移和最大长度在 workflow 与 TF-A 之间一致，并检查
``board/airoha/xg2010g/atf/build-atf.sh`` 的开关：一旦它定义
``TCSUPPORT_UBI_SUPPORT`` 就报错，因为那会让 ``plat_ecnt_io_setup()`` 用
``fip_ubi_policy`` 覆盖无条件的 ``fip_memmap_policy``，BL23 改从 UBI 卷
``fip`` 读取第二阶段 FIP，而该路径把 UBI 定位在 ``UBI_START_ADDR``（TF-A
默认 ``0x20000``，可用 ``OVERRIDE_UBI_START_ADDR`` 覆盖），与本布局的
``ubi@0x600000`` 不兼容；同时要求它保留 ``TCSUPPORT_EMMC=1``，那是
``bl2_image_load_v2.c`` 中 memmap/XMODEM 救援路径唯一的编译开关
（本板没有 eMMC）。

第三项检查是 ``mk-flag-coverage``：它会扫出 TF-A 树里所有以 make 变量形式
判断的 ``TCSUPPORT_*``，要求 ``build-atf.sh`` 显式传值，或在脚本内的
``MK_FLAG_ALLOWLIST`` 里写明"不传就是我们要的那一支"的理由。这一项存在的
原因是 ``add_define`` 只生成编译期 ``-D``，不会创建 make 变量，所以
"由 ``TCSUPPORT_CPU_EN7581`` 派生" 的宏在 ``$(...)`` 判断里读到的是空值 ——
例如 ``platform.mk`` 用 ``ifneq ($(TCSUPPORT_UBOOT_64BIT),1)`` 决定是否打开
``INIT_UNUSED_NS_EL2``，漏传就会让 BL31 改写一组 EL2 寄存器。

上面这些检查在 CI 中分两道执行：仓库内的部分在安装工具链之前跑
（秒级失败），涉及 TF-A 的部分在 TF-A 树就绪后跑。

XR1710G 差异
------------

Brightspeed Gemtek XR1710G 与 XG2010G 共用同一套启动链、NAND 分区布局、工厂校准数据处理
和 Recovery 流程，因此由同一份板级支持代码（``board/airoha/an7581``）同时
服务两板，仅通过设备树区分硬件差异。XR1710G 使用
``configs/xr1710g_defconfig`` 与 ``arch/arm/dts/xr1710g.dts`` 构建，
板级 compatible 为 ``gemtek,xr1710g(-ubi)`` 与
``econet,xr1710g(-ubi)``。

XR1710G 的硬件差异要点（依据实测可用的 XR1710G-http-uboot chainloader 与
ImmortalWrt ``an7581-xr1710g-ubi.dts``）：

* 内存为 2 GiB DDR（XG2010G 为 1 GiB）；
* 面板状态灯 sts 红/绿/蓝/白 位于统一 ``en7581_pinctrl`` 的 GPIO
  29/17/19/20（低有效），与 XG2010G 的 43/44/45/33 不同；
* 两个外部 Realtek PHY（phy5/phy8）与 XG2010G 一样挂在 FE MDIO
  （``airoha,arht-mdio``），不在交换芯片 MDIO 上；phy5 复位 GPIO 为 46，
  phy8 复位 GPIO 为 31，均为低有效，且需要 ``realtek,pnswap-tx/rx`` 极性
  交换；交换芯片保持原生端口映射（内部 PHY 9/10），本仓库 U-Boot 的
  switch 自动轮询窗口固定为 8..12，刚好覆盖 9/10 与 XG2010G 的 12；
* ``gdm4`` 通过 USXGMII 连接 phy5，``gdm2`` 通过 USXGMII 连接 phy8；
  ``gdm1`` 仍为交换芯片 CPU 口，LAN1/LAN2 两个网口由内部交换口提供；
* LAN1/LAN2 网口绿/黄灯是软件 GPIO（绿 43/44、黄 33/34，低有效），
  恢复页按链路速度点亮：千兆亮绿灯、10/100M 亮黄灯、有流量时 100ms
  周期闪烁；XG2010G 的 LAN4 口绿/黄灯（46/42）同理；
* MDIO 引脚组额外包含 ``gpio2`` 输出高电平的 conf，与 ImmortalWrt 板级
  DTS 和 chainloader 保持一致；
* RESET 键同为 ``en7581_pinctrl`` GPIO 0，低有效，Recovery 行为与 XG2010G
  完全一致。

Recovery 仅启用并监听 ``eth0`` / ``gdm1``，即内部 switch CPU 口提供的
1G 网口。XG2010G 的 RTL8261N/EN8811H XSI 口、XR1710G 的 phy5/phy8
USXGMII 口不在 U-Boot recovery DTS 中启用，避免多 MAC 随机地址和多个
``192.168.0.1`` netif 同时收发导致 TCP 冲突。两板的 Web Recovery 地址、
无痕模式要求和 UBI 重建流程相同。

恢复网页资源
------------

恢复页面的源文件在 ``lib/lwip/httpd/htdocs_recovery/``，编译前需要先打包成
``lib/lwip/httpd/fsdata_recovery.c``：

.. code-block:: console

    python3 lib/lwip/httpd/makefsdata.py

源文件与生成的 ``fsdata_recovery.c`` 要一起提交。只改 HTML 而不重新生成，
设备上看到的仍然是旧页面。

页面里不写死板型。型号由恢复服务器通过 ``/about`` 端点的 ``board`` 字段
给出（取自 ``CONFIG_DEFAULT_DEVICE_TREE``），前端在运行时注入，因此几块板
可以共用同一份页面资源，不会出现 XR1710G 显示 XG2010G 的情况。
